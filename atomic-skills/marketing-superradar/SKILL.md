# Маркетинговый Суперрадар

Искать новые рыночные сегменты не одной эвристикой, а параллельным набором независимых радаров. Отделять **обнаружение сигнала**, **проверку рынка**, **поиск точки входа** и **adversarial re-check**. Не защищать первоначально понравившуюся идею: понижать или убивать её, если прямые конкуренты уже закрывают найденный процесс.

## Когда применять

Применять при запросах на:

- еженедельный поиск новых стартап-возможностей;
- поиск новых рыночных сегментов;
- анализ идеи по «Суперрадару»;
- поиск коммерциализирующихся технологий на горизонте 1–3 года;
- поиск денежных утечек, дорогого ручного труда или регуляторно создаваемых рынков;
- поиск «незанятого места» после конкурентного анализа;
- оценку TAM / SAM / SOM / SAMconc;
- поиск 3–5 малозатратных векторов входа;
- разбор второго эшелона, например позиций 11–20;
- повторную конкурентную проверку ранее найденной идеи.

Не применять как обычный brainstorm без рыночной проверки. Не выдавать красивую идею за opportunity, пока не найден payer, trigger и evidence.

## Справочники

Перед полным запуском прочитать:

- [references/radar-taxonomy.md](references/radar-taxonomy.md) — 13 радаров, сигналы и поисковые эвристики.
- [references/scoring-and-output.md](references/scoring-and-output.md) — scoring, evidence audit, конкурентная проверка, SAMconc, шаблоны финального отчёта.

Для особенно спорных финалистов применять принципы `the-fool`: falsification, competing explanations, pre-mortem и red-team. Не требовать от пользователя выбора режима, если запрос уже явно требует adversarial re-check.

## Базовые допущения

Если пользователь не задал иное:

- использовать текущие данные, а не знания «вообще»;
- основной горизонт коммерциализации: 1–3 года;
- предпочитать возможности, где MVP небольшой команды реалистичен за 8–12 недель;
- предпочитать рынки с измеримым money event, обязательностью, дорогим ручным процессом или переходом к новому состоянию;
- считать `SAMconc = SAM × (1 − competition_score / 10)`;
- давать ответ на русском, если запрос на русском; английские термины сразу переводить или расшифровывать;
- показывать модельные оценки рынка как **расчётные диапазоны**, а не как опубликованные market-report numbers.

## Обязательная политика доказательств

1. Искать свежие внешние данные для всех изменчивых рыночных фактов.
2. Предпочитать первичные источники: регуляторов, компаний, procurement notices, официальные product docs, отчёты, filings, research institutions.
3. Использовать Reddit, форумы, reviews и сообщества как evidence боли, но не как единственное доказательство рынка.
4. Для каждого важного тезиса различать:
   - факт из источника;
   - оценку/расчёт;
   - гипотезу;
   - вывод.
5. Проверять даты событий отдельно от дат публикаций.
6. Не выводить рынок только из vendor marketing.
7. Для каждого финалиста искать не только category competitors, но и **точное совпадение workflow**.
8. Если источник не поддерживает цифру — не придумывать её. Строить bottom-up модель и явно показывать assumptions.
9. Применять falsification: формулировать, что именно должно оказаться истинным, чтобы идею пришлось убить.

## Основной процесс

### 1. Задать рамку запуска

Зафиксировать:

- дату среза;
- географию, если указана;
- B2B/B2C/оба;
- ограничения по капиталу и сроку MVP;
- исключённые отрасли;
- нужен ли полный top-10, только top-3, позиции 11–20 или одна конкретная идея.

Не задавать уточняющий вопрос, если рамку можно разумно вывести из контекста.

### 2. Просканировать 13 радаров параллельно

Использовать полный список из `radar-taxonomy.md`.

Для каждого найденного сигнала фиксировать минимум:

- что произошло;
- кто испытывает боль или обязанность;
- кто платит;
- какой trigger создаёт покупку;
- какой money event измеряется;
- почему окно открывается сейчас;
- доступные данные/evidence;
- возможный MVP;
- ближайшие прямые и косвенные конкуренты.

Не ограничиваться AI. Допускать construction, industrial, fintech, insurance, logistics, compliance, healthcare, education, robotics, commerce и другие отрасли.

### 3. Сформировать широкий пул кандидатов

Для полного еженедельного запуска стремиться собрать 20–40 кандидатов, затем дедуплицировать их по underlying job-to-be-done.

Объединять идеи, если у них совпадают:

- buyer;
- trigger;
- input data;
- workflow;
- measurable outcome.

Не считать разными стартапами одно и то же решение с разными названиями.

### 4. Провести первичный evidence audit

Для каждого кандидата проверить:

- **Problem evidence:** есть ли реальная боль/обязательство/потеря;
- **Budget evidence:** существует ли budget owner;
- **Timing evidence:** почему сейчас, а не через пять лет;
- **Workflow evidence:** есть ли повторяющийся процесс;
- **Data evidence:** можно ли наблюдать input и проверить output;
- **Competitive evidence:** кто уже закрывает этот workflow.

Понижать идеи, основанные только на тренде, funding headline или одном ярком incident.

### 5. Оценить кандидатов

Применить scoring из `scoring-and-output.md`.

Оценивать как минимум:

- сила боли / денег / обязательности;
- размер достижимого рынка;
- рост;
- срочность;
- платёжеспособность buyer;
- доступность данных;
- реалистичность MVP 8–12 недель;
- конкурентный разрыв.

Отбирать 10 лучших для таблицы и 4–5 для углублённой проверки.

### 6. Выполнить глубокий анализ финалистов

Для каждого финалиста пройти строго:

`TAM → competitors/substitutes → Competitive Gap → entry vectors → adversarial re-check → wedge v2 → SAM → competition → SAMconc → SOM 1y → MVP → risks → kill criteria`.

Не менять порядок: слишком ранний wedge создаёт confirmation bias.

### 7. Разложить Competitive Gap

Оценить шесть разрывов:

1. **Продуктовый** — отсутствует ли нужная функция/объект.
2. **Процессный** — ломается ли handoff между этапами/системами/ролями.
3. **Дистрибуционный** — можно ли добраться до buyer дешевле incumbents.
4. **Бизнес-модели** — можно ли убрать upfront-risk, seats или CAPEX.
5. **Доверия/внедрения** — можно ли начать в shadow mode, read-only или human-in-the-loop.
6. **Перехода** — возникает ли новый момент покупки при regulatory deadline, renewal, pilot→production, read→write, one→fleet и т.п.

Отдельно отличать **feature gap** от **structural workflow/control gap**. При feature gap ожидать быструю копируемость incumbent-ом.

### 8. Сформировать 3–5 малозатратных векторов входа

Обязательно рассмотреть пять базовых классов:

- **продуктовый клин** — узкая критичная функция;
- **встраивание в рабочий процесс** — sidecar/overlay без замены core system;
- **триггер перехода** — renewal, audit, incident, rollout, migration, regulation deadline;
- **арбитраж дистрибуции** — новый канал, white-label, integrator/MSP/accountant/broker/consultant;
- **арбитраж бизнес-модели** — success fee, outcome pricing, audit→software, service→software, usage pricing.

Не предлагать все пять механически. Выбирать 3–5 наиболее правдоподобных.

### 9. Провести adversarial competitor re-check каждого вектора

Для каждого entry vector искать:

- конкурента с тем же buyer;
- конкурента с тем же trigger;
- конкурента с тем же input/output;
- incumbent feature, который может закрыть gap;
- service substitute;
- internal build;
- adjacent platform.

После проверки помечать:

- ✅ выжил;
- ⚠️ выжил только после сужения;
- ❌ убить.

Не «спасать» слабый вектор сменой формулировки без изменения workflow.

### 10. Сформулировать wedge v2

Оставлять только клин, переживший повторную проверку.

Формулировать в виде:

> Для [узкий ICP], когда происходит [trigger], продукт получает [input/evidence], выполняет [проверяемый workflow] и выдаёт [измеримый outcome], не требуя [дорогая замена/опасное permission/долгое внедрение].

Для 13-го радара добавлять:

> Intended/Approved State → External/Actual State → Reconciliation → Evidence Receipt.

### 11. Посчитать рынок

Показывать отдельно:

- **TAM** — весь экономически релевантный рынок;
- **SAM** — достижимый сегмент для wedge v2;
- **Competition 0–10** — насыщенность именно wedge v2, а не общей категории;
- **SAMconc** — `SAM × (1 − competition/10)`;
- **SOM 1y** — реалистичная выручка первого года снизу вверх.

Для SOM предпочитать:

`количество реально достижимых клиентов × реалистичный годовой чек`

или для success fee:

`клиенты × выявленный recoverable value × take rate`.

Не выдавать SOM как долю TAM без go-to-market логики.

### 12. Проверить MVP

Разделить:

- что обязательно для paid pilot;
- что можно сделать вручную;
- что можно взять готовым API/integration;
- что нельзя строить в MVP;
- time-to-pilot;
- ключевой data dependency.

Предпочитать путь:

`manual audit/service → shadow mode → assisted workflow → software enforcement`.

### 13. Задать 7-дневный тест и kill criteria

Для финального лидера сформировать:

- 3–5 проверок на ближайшие 7 дней;
- measurable continuation threshold;
- 3–5 kill criteria;
- самые опасные конкурирующие объяснения успеха сигнала.

Пример: «5 из 10 buyers считают проблему своей» сильнее, чем «интервью прошли позитивно».

### 14. Сформировать итог

Для полного запуска выводить:

1. top-10 таблицу;
2. краткое объяснение сигналов недели;
3. глубокий разбор top-3;
4. ещё 1–2 финалиста короче;
5. идеи, убитые adversarial re-check;
6. победителя недели;
7. лучший малозатратный entry vector;
8. проверки на 7 дней;
9. kill criteria;
10. отдельный блок по радару №13.

Если запрошены позиции 11–20, использовать отдельный second-echelon формат из `scoring-and-output.md`, не повторяя top-10.

## Особое правило радара №13

Повышать score, если:

- одна сторона контролирует intended/approved state;
- другая система или организация может изменить объект;
- третья сторона несёт риск/ответственность;
- фактическое состояние можно наблюдать только после межсистемной границы;
- drift обнаруживается поздно;
- drift создаёт денежный, регуляторный или физический риск;
- проверку можно начать read-only/shadow mode.

Такие случаи часто сильнее обычного «сравнить две записи», потому что incumbent одной системы не контролирует другую систему.

## Нежелательные паттерны

Не считать хорошим рынком:

- «AI для X» без buyer/trigger;
- generic dashboard;
- generic copilot;
- ещё одну GRC/TPRM/FinOps platform без structural gap;
- scanner, если scanner уже стал commodity;
- compliance assistant, если обязанность редкая и annual recurring value не доказана;
- workflow, который incumbent может закрыть одной простой настройкой;
- рынок, где данные недоступны без тяжёлого внедрения;
- слишком раннюю технологию без budget/production signals;
- TAM, построенный только сверху вниз по отраслевому отчёту.

## Режимы использования

### Weekly Full Scan

Собрать 20–40 кандидатов → top-10 → deep top-3 → победитель.

### Single Opportunity Deep Dive

Прогнать одну идею через все этапы без искусственного сравнения с 20 кандидатами.

### Second Echelon 11–20

Восстановить кандидатов за пределами top-10, проверить, почему каждый не вошёл в первую десятку, и искать способы устранить основной дефект.

### Commercialization Focus

Усилить радары 2, 5, 6, 7, 11 и 12; искать horizon 1–3 years.

### State Assurance Focus

Усилить радар 13; искать `declared/approved/authorized/contracted → actual` drift.

## Критерий качества

Считать запуск успешным, если финальный отчёт позволяет ответить:

- **Почему этот рынок существует?**
- **Почему окно открыто сейчас?**
- **Кто платит и из какого бюджета?**
- **Почему incumbent ещё не закрыл gap?**
- **Как войти без лобовой конкуренции?**
- **Какой факт убьёт гипотезу в течение недели?**

Если на один из этих вопросов нет ответа, считать идею невалидированной.
