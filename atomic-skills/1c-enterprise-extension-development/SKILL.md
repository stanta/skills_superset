# 1С:Предприятие — разработка расширений конфигурации

## 0. Назначение скилла

Используй этот скилл, когда задача связана с **расширением конфигурации 1С:Предприятие (`.cfe`)**: добавлением функциональности к типовой или отраслевой конфигурации без снятия основной конфигурации с поддержки, интеграцией с внешними API, фоновыми заданиями, ролями, формами, регистрами, тестами, обновлениями и CI/CD.

Не путай расширение конфигурации с:

- внешней обработкой/отчетом (`.epf/.erf`);
- расширением платформы / внешней компонентой;
- плагином 1C:EDT на Java/Eclipse;
- форком основной конфигурации.

Если задача может быть решена расширением без модификации типовой конфигурации, **extension-first является вариантом по умолчанию**. Прямую модификацию основной конфигурации допускай только при доказанной технической необходимости и с явным описанием цены обновлений.

---

## 1. Базовая установка перед разработкой

До написания кода установи и зафиксируй в проекте следующие параметры:

```text
base_configuration: <имя + точный релиз>
platform_target: <точная версия платформы>
compatibility_mode: <режим совместимости основной конфигурации>
extension_purpose: <назначение расширения>
extension_prefix: <уникальный префикс>
interface: <managed application / другое>
BSP: <есть/нет + версия, если известна>
runtime_modes: <server/file/web/thin client — фактически поддерживаемые>
DBMS: <поддерживаемые СУБД>
```

### Текущий инструментальный baseline

На сентябрь 2026 для стабильного CI/командной разработки ориентируйся на **релизную 1C:EDT 2026.1.x**, а release candidate 2026.2 используй только при осознанном opt-in. Не повышай версию платформы или режим совместимости «ради новизны»: расширение должно соответствовать реально поддерживаемой основной конфигурации и ее инфраструктуре.

Правило: **версия платформы, режим совместимости и релиз базовой конфигурации — часть контракта расширения**.

---

## 2. Главный архитектурный принцип: не ломать поддержку

Расширение должно минимально зависеть от внутреннего устройства типовой конфигурации.

Предпочтительный порядок интеграции:

1. публичный программный интерфейс конфигурации/библиотеки;
2. механизмы БСП и переопределяемые модули, если они предусмотрены;
3. подписки/события и штатные точки расширения;
4. `&Перед` / `&После`;
5. `&Вместо` только при отсутствии безопасной альтернативы.

Чем глубже пункт, тем выше upgrade-risk.

**Запрещено** проектировать расширение так, чтобы успешное обновление зависело от копирования больших фрагментов типового кода внутрь расширения.

---

## 3. Минимизируй поверхность заимствования

Заимствуй только те объекты и свойства основной конфигурации, которые реально нужны расширению.

Не делай «заимствовать весь документ/форму/подсистему на всякий случай». Каждый заимствованный объект — дополнительная точка проверки совместимости после обновления основной конфигурации.

При ревью для каждого заимствованного объекта должен быть понятен ответ:

```text
Почему он заимствован?
Какой именно контракт расширения от него зависит?
Что произойдет при его изменении в типовой конфигурации?
Есть ли менее связанный способ?
```

---

## 4. Префикс обязателен и стабилен

У расширения должен быть уникальный префикс. Новые объекты, роли, общие модули, регистры, команды, HTTP-сервисы и служебные сущности именуй последовательно с этим префиксом.

Нельзя менять префикс без миграционного плана после выхода расширения в production.

Для Orbitas используй один согласованный префикс во всем расширении; не смешивай `ORB`, `Orbitas`, `Орб` и другие варианты в одном проекте.

---

## 5. Назначение расширения — часть семантики

Выбирай назначение расширения осознанно и документируй его. Не используй режим «исправление» как универсальный способ обойти ограничения совместимости.

Для продуктовой функциональности, добавляющей интеграцию или новые объекты, исходи из назначения, соответствующего **дополнению/адаптации**, а не из временного patch-mode, если нет задачи исправить конкретный дефект поставщика.

---

## 6. Стратегия расширения методов

### 6.1 `&Перед` и `&После` — предпочтительно

Используй их, когда требуется:

- проверить предусловия;
- добавить подготовку данных;
- дополнить результат стандартного действия;
- зарегистрировать событие;
- создать собственную побочную запись после успешного стандартного действия.

Они сохраняют выполнение базового метода и обычно лучше переживают обновления.

### 6.2 `&Вместо` — высокий риск

Используй `&Вместо` только если:

- стандартный метод действительно требуется заменить или обрамить;
- нет публичного API или `&Перед/&После`;
- задокументирована зависимость от сигнатуры и поведения базового метода;
- есть regression-test на поведение после обновления базовой конфигурации.

Где возможно, `&Вместо` должен вызывать `ПродолжитьВызов()` и менять лишь необходимую часть поведения.

### 6.3 Никогда не копируй типовой метод целиком без причины

Если приходится скопировать код поставщика, пометь участок как upgrade hotspot, укажи точный релиз-источник и включи обязательную diff-проверку при обновлении.

---

## 7. Разделяй слои

Для интеграционного расширения держи четкие слои:

```text
UI / Commands
    ↓
Application service
    ↓
Domain mapping / validation
    ↓
Persistence / registers
    ↓
Outbox / background execution
    ↓
HTTP transport
```

Не размещай HTTP-вызовы, сериализацию JSON, бухгалтерскую логику, запись регистров и UI-уведомления в одной процедуре формы.

Типовая структура общих модулей для внешней интеграции:

```text
<Prefix>Клиент
<Prefix>Сервер
<Prefix>Служебный
<Prefix>Интеграция
<Prefix>HTTP
<Prefix>JSON
<Prefix>Очередь
<Prefix>Переопределяемый   // если реально нужен публичный extension point
```

Имена должны описывать назначение, а не просто «Процедуры»/«Функции».

---

## 8. Публичный API расширения проектируй как контракт

Экспортная процедура/функция считается API. Для нее обязательно:

- стабильное имя;
- документированные параметры и возвращаемое значение;
- явная семантика ошибок;
- минимальный набор экспортных методов;
- отсутствие утечки внутренних объектов хранения, если потребителю достаточно DTO/структуры;
- совместимость при минорных обновлениях.

Не делай все процедуры `Экспорт` «для удобства».

---

## 9. Серверная бизнес-логика, тонкий клиент

Бизнес-логику, запросы, интеграцию и работу с БД выполняй на сервере. На клиенте оставляй только то, что действительно относится к интерфейсу и дешевле локального выполнения, чем серверного вызова.

Минимизируй количество клиент-серверных вызовов. Одно пользовательское действие должно по возможности приводить к одному осмысленному серверному вызову, а не к каскаду мелких запросов.

Не передавай между клиентом и сервером большие таблицы/объекты, если можно передать идентификаторы или компактный DTO.

---

## 10. Запросы и производительность

Обязательные правила:

- не выполняй запрос в цикле, если данные можно получить пакетно;
- фильтруй максимально рано;
- используй индексы и эффективные условия;
- не тащи лишние поля;
- избегай N+1 обращений к объектам;
- для массовых операций предпочитай наборы записей и пакетные алгоритмы;
- измеряй тяжелые запросы на реалистичном объеме данных;
- учитывай разные СУБД, поддерживаемые платформой;
- не оптимизируй за счет нештатного SQL мимо платформы без отдельного архитектурного решения.

Performance-test должен включать «холодный» и повторный запуск, а для интеграций — большой backlog очереди.

---

## 11. Транзакции

Транзакции должны быть короткими, локальными и полностью управляться одним методом.

Правильный каркас:

```bsl
НачатьТранзакцию();
Попытка
    // чтение, блокировки, проверки и запись
    ...
    ЗафиксироватьТранзакцию();
Исключение
    ОтменитьТранзакцию();
    ВызватьИсключение;
КонецПопытки;
```

Требования:

- `НачатьТранзакцию` и фиксация/отмена — в одном методе;
- `НачатьТранзакцию` — непосредственно перед `Попытка`;
- `ЗафиксироватьТранзакцию` — последнее действие в `Попытка`;
- в `Исключение` сначала `ОтменитьТранзакцию`;
- не держать транзакцию во время длительных вычислений;
- **не выполнять HTTP/FTP/почту/сетевые ресурсы внутри транзакции**;
- явно продумывать управляемые блокировки при конкурирующих изменениях.

---

## 12. Внешние API: никакого HTTP внутри критической записи

Нельзя строить надежную интеграцию по схеме:

```text
Запись документа → HTTP POST → если не ответил, откатить все
```

Это связывает доступность 1С с доступностью внешней системы и создает неопределенные состояния при таймаутах.

По умолчанию используй **durable outbox**:

```text
Локальная транзакция:
  бизнес-факт + запись Outbox
COMMIT

Фоновый worker:
  взять Outbox
  отправить HTTP
  обработать ответ
  записать результат / retry
```

HTTP-вызов выполняется вне транзакции бизнес-документа.

---

## 13. Durable Outbox для 1С

Для серьезной интеграции заводи отдельное хранилище очереди — обычно регистр сведений/специализированный объект, а не реквизиты типового документа.

Минимальная модель сообщения:

```text
MessageId             UUID
IdempotencyKey        String
EventType             String
SourceType            String
SourceId              String
PayloadVersion        Integer/String
Payload               JSON/Binary
Status                New|Processing|Sent|Retry|Failed|DeadLetter
Attempt                Integer
NextAttemptAt         DateTime
CreatedAt             DateTime
LastAttemptAt         DateTime
LastHTTPStatus         Integer
LastErrorClass         String
LastErrorText          String (bounded)
CorrelationId         String
RemoteId              String
```

Требования:

- создание outbox-записи в той же локальной транзакции, что и событие, породившее интеграцию;
- уникальность `IdempotencyKey`;
- повторная отправка безопасна;
- `Processing` имеет lease/timeout, чтобы запись не зависла после падения сеанса;
- permanent error отделяется от retryable error;
- предусмотрен dead-letter workflow и ручной requeue;
- payload versioned.

---

## 14. Идемпотентность обязательна

Каждая внешняя write-операция должна иметь стабильный ключ идемпотентности.

Хорошая схема ключа:

```text
<tenant>/<source-system>/<source-object-id>/<event-kind>/<business-version>
```

Не используй текущую дату/время или случайный UUID как единственную основу ключа повторяемой бизнес-операции.

Обработчик входящего webhook/response также должен быть идемпотентным: повтор одного и того же remote event не должен создавать вторую оплату, вторую связь или второе обязательство.

---

## 15. Retry policy

Для HTTP-интеграции разделяй ошибки:

```text
Retryable:
- timeout
- DNS/transient network
- 408
- 429
- 5xx

Usually permanent / manual:
- invalid payload / schema mismatch
- 401/403 после refresh/credential re-check
- 404 для обязательного remote object
- business validation rejection
```

Используй exponential backoff + jitter и верхнюю границу числа попыток.

Не делай tight-loop retry в пользовательском сеансе.

---

## 16. Таймауты и HTTPS

Для каждого внешнего ресурса таймаут должен быть задан явно. «Бесконечный» таймаут недопустим.

Для HTTPS:

- проверяй подлинность удаленного сервера;
- используй системное/доверенное хранилище CA;
- не отключай проверку сертификата ради «быстрого исправления»;
- не разрешай HTTP downgrade для production endpoints;
- hostname/endpoints должны быть конфигурируемыми по окружениям.

Сетевое соединение — недоверенная граница, даже если сервер «наш».

---

## 17. Секреты

Никогда не храни API token/private key:

- в коде;
- в Git;
- в макете;
- в строковой константе расширения, доступной всем пользователям;
- в журнале регистрации;
- в полном HTTP request/response dump.

Если базовая конфигурация/БСП предоставляет механизм безопасного хранения учетных данных — используй его. Иначе создай отдельный защищенный механизм хранения с минимальными ролями и шифрованием/защитой средствами целевой инфраструктуры.

Логи содержат fingerprint/credential-id, но не secret.

---

## 18. Безопасность: собственные роли расширения

Не заимствуй и не изменяй роли `ПолныеПрава` и `АдминистраторСистемы` только ради расширения.

Создавай собственные роли по модели 1С, например:

```text
<Prefix>ОбщиеПрава

или

<Prefix>ПолныеПрава
<Prefix>БазовыеПрава
<Prefix>БазовыеПраваВнешнихПользователей
```

При наличии БСП используй профили групп доступа и штатную модель управления правами.

Роли должны быть атомарными там, где требуется гибкое администрирование.

---

## 19. Проверяй право, а не название роли

Когда нужна проверка доступа к объекту, предпочитай `ПравоДоступа(...)`, а не жесткую привязку бизнес-кода к конкретной роли.

`РольДоступна(...)` используй только когда роль действительно является отдельным дополнительным разрешением и ее смысл нельзя выразить правом на объект.

Не делай безопасность только через скрытие кнопки: серверный метод обязан самостоятельно соблюдать модель доступа.

---

## 20. Привилегированный режим — минимальный и локальный

Привилегированный режим не является заменой правильной модели прав.

Правила:

- минимальный участок кода;
- причина должна быть понятна из кода/комментария;
- не принимать произвольный код/запрос пользователя и исполнять его привилегированно;
- валидировать входные идентификаторы и tenant/organization scope до входа в привилегированный участок;
- публичный серверный API с привилегиями рассматривается как security-critical.

---

## 21. Safe mode и внешний код

Если расширение или обработка может исполнять внешние формулы, код, подключаемые компоненты или динамические выражения — используй безопасный режим и минимальные права.

Не ослабляй safe-mode глобально ради одной интеграционной функции.

Установка внешней компоненты должна быть осознанным интерактивным действием пользователя/администратора, если платформа не предоставляет иной доверенный deployment mechanism.

---

## 22. Ошибки: не глотать

Антипаттерн:

```bsl
Попытка
    ...
Исключение
КонецПопытки;
```

Если исключение перехвачено, должно быть одно из трех:

1. оно преобразовано в понятную бизнес-ошибку;
2. выполнен осмысленный fallback;
3. оно залогировано с диагностикой и перевызвано/передано выше.

Не показывай конечному пользователю raw stack/секреты/полный payload внешней системы.

---

## 23. Наблюдаемость

Используй Журнал регистрации для действительно полезной диагностики, но не как high-volume message store.

Для интеграционного расширения должны коррелироваться:

```text
CorrelationId
MessageId
IdempotencyKey
LocalSourceId
RemoteId
Attempt
DurationMs
ResultClass
HTTPStatus
```

Большие payload/response не помещай в Журнал регистрации. Если требуется технический архив сообщений — проектируй отдельное ограниченное хранилище с retention policy и masking.

---

## 24. Фоновые и регламентные задания

Периодическую интеграцию выполняй фоново/регламентно, но:

- не запускай задание чаще, чем нужно бизнесу;
- отключай его, если функциональность интеграции выключена;
- параметризованные задания не должны плодиться бесконтрольно;
- обеспечь защиту от параллельной обработки одной outbox-записи;
- тяжелые пачки дроби на bounded batches;
- пользователь должен видеть состояние очереди и иметь контролируемый manual retry;
- для сервиса/разделенной ИБ учитывай ограничения очереди заданий.

Если внешняя система умеет push/webhook, не заменяй его бесконечным частым polling без причины.

---

## 25. Работа с данными типовой конфигурации

### 25.1 Не меняй производные учетные данные напрямую

Не записывай «готовый результат» прямо в регистры/остатки/взаиморасчеты только потому, что так проще.

Предпочитай:

1. штатный документ;
2. публичный API типовой конфигурации;
3. поддерживаемую бизнес-операцию;
4. собственные данные расширения, если внешний факт еще не является бухгалтерским фактом.

### 25.2 Статус интеграции ≠ статус учета

Например:

```text
remote settlement instruction created
```

не означает автоматически:

```text
долг погашен в 1С
```

До получения юридически/учетно достаточного подтверждения храни внешний статус отдельно.

---

## 26. Multi-company / организации / разделение данных

Любая интеграция должна явно знать, к какой организации/области данных относится запись.

Нельзя:

- выбирать «первую организацию»;
- искать credential без scope организации;
- смешивать outbox разных tenants;
- принимать remote callback без проверки принадлежности сущности этой организации.

Тесты должны содержать минимум две организации с разными правами и credentials.

---

## 27. Валюты, суммы и округление

Для денежных интеграций:

- не конвертируй `Число` в binary float во внешнем JSON без контролируемой decimal-семантики;
- сохраняй валюту рядом с суммой;
- различай документную, управленческую и регламентированную валюту;
- определяй правило округления на границе систем;
- не сравнивай денежные значения «на глаз» после конвертации;
- partial payment/partial settlement — сценарий первого класса.

---

## 28. Время и даты

Зафиксируй семантику времени:

```text
business_date
source_timestamp
created_at
sent_at
remote_timestamp
```

Не смешивай дату документа с техническим timestamp.

При обмене с внешней системой передавай timezone/UTC по согласованному контракту. Не полагайся на локальное время клиента.

---

## 29. JSON и контракты интеграции

Сериализация должна быть отдельным слоем.

Правила:

- schema/version в payload;
- обязательные поля валидируются до отправки;
- unknown optional fields на входе по возможности игнорируются;
- breaking change требует новой версии;
- 1С-ссылки и внутренние представления типов не должны утекать наружу как публичный контракт;
- enum/status передаются стабильными строковыми кодами, не локализованным представлением.

---

## 30. Webhook / HTTP-сервис внутри 1С

Если расширение публикует HTTP-сервис:

- authentication обязательна;
- authorization проверяется на сервере;
- request body ограничен по размеру;
- content type проверяется;
- schema validation выполняется до бизнес-записи;
- replay/idempotency защита обязательна;
- не выполнять долгую обработку синхронно — принять, зафиксировать inbox и вернуть ответ;
- secret/signature сравнивать безопасно;
- журналировать correlation id, но не секреты;
- rate/abuse controls проектируются на уровне gateway/web server, если платформа сама не покрывает задачу.

Для надежного входящего потока используй **durable inbox** по той же логике, что и outbox.

---

## 31. Inbox pattern

Минимальная модель входящего события:

```text
RemoteEventId
EventType
ReceivedAt
PayloadHash
PayloadVersion
Status
Attempt
LastError
CorrelationId
```

Сначала атомарно сохраняй входящее событие, затем обрабатывай его. Повторное событие с тем же `RemoteEventId` не должно повторять бизнес-эффект.

---

## 32. Миграции и обновления расширения

Любое изменение структуры данных должно иметь upgrade plan.

При БСП используй штатные обработчики обновления информационной базы. Миграция должна быть:

- versioned;
- idempotent;
- повторно запускаемой;
- без интерактивных вопросов;
- детерминированной;
- по возможности batch/отложенной на больших объемах;
- не зависящей от случайного порядка нескольких обработчиков одной версии.

Не делай миграцию миллионов записей монопольным блоком, если это можно безопасно выполнить отложенно.

---

## 33. Совместимость с обновлениями основной конфигурации

Каждый новый релиз базовой конфигурации проходит compatibility gate:

```text
1. Загрузить/обновить base configuration.
2. Проверить применимость расширения.
3. Проверить ошибки заимствованных объектов и расширенных методов.
4. Выполнить EDT validation / стандарты разработки.
5. Собрать .cfe заново.
6. Поднять чистую тестовую ИБ на новом base release.
7. Установить расширение.
8. Выполнить upgrade handlers.
9. Прогнать unit/integration tests.
10. Прогнать ключевой E2E smoke.
11. Проверить uninstall/deactivation behavior, если это поддерживаемый сценарий.
```

Не объявляй релиз совместимым только потому, что `.cfe` подключился без синтаксической ошибки.

---

## 34. Тестовая стратегия

Используй пирамиду:

### 34.1 Unit / component

Проверяй чистые функции:

- mapping;
- validation;
- idempotency key generation;
- JSON encode/decode;
- retry classification;
- amount/date normalization.

Для BSL-тестов можно использовать YAxUnit или принятый в команде equivalent.

### 34.2 Integration

Проверяй:

- запись объектов расширения;
- обработчики событий типовой конфигурации;
- rights;
- outbox/inbox;
- migration;
- регламентные задания;
- mock/stub HTTP boundary.

### 34.3 E2E / BDD

Для критичных пользовательских сценариев используй сценарное тестирование, например Vanessa Automation, если это соответствует стеку проекта.

Не заменяй unit/integration тесты исключительно UI-сценариями.

## 36. Статический анализ и quality gate

В CI обязательны:

1. проверка проекта 1C:EDT;
2. плагин **«1С:Стандарты разработки V8»**;
3. при необходимости дополнительный анализ BSL Language Server;
4. отсутствие новых blocking/error diagnostics;
5. осознанные suppressions с комментарием, а не глобальное отключение правил.

BSL Language Server — полезный дополнительный анализатор, но не заменяет проверку реальной метамодели расширения средствами 1C:EDT/платформы.

## 39. Semantic versioning для расширения

Даже если платформа не навязывает SemVer, продуктовая дисциплина должна быть близка к ней:

```text
MAJOR — breaking API/data/installation change
MINOR — backward-compatible feature
PATCH — backward-compatible fix
```

Версия должна быть доступна программе и отображаться администратору.

Изменение data schema всегда сопровождается migration note.

## 40. Feature flags

Рискованные или поэтапно включаемые функции делай отключаемыми:

- функциональная опция / настройка;
- organization-scoped enablement, если нужно;
- kill switch для внешней интеграции;
- отдельно «принимать входящие» и «отправлять исходящие», если operationally useful.

Выключение интеграции не должно уничтожать очередь/историю.

---

## 41. Формы и UX

Не усложняй типовые формы без необходимости.

Предпочитай:

- отдельную команду;
- отдельное рабочее место;
- компактный статус расширения;
- стандартные элементы UI;
- асинхронную длительную операцию вместо «заморозки» формы.

Не делай UI единственным способом восстановить сбой интеграции: администратор должен иметь диагностируемый системный статус.

---

## 42. Инструменты администратора расширения

Production-интеграция должна иметь административное рабочее место минимум с:

```text
connection status / health
configured organization(s)
last successful sync
queue depth
retry count
dead-letter count
recent errors
credential metadata (without secret)
manual retry/requeue
pause outbound
pause inbound
version/build info
```

Нужна команда `Проверить соединение`, которая не создает бизнес-данных.

---

## 43. Не использовать журнал регистрации как очередь

Журнал регистрации — аудит и диагностика, не durable transport.

Не строить обработку «найти в ЖР все события документа и отправить наружу» как основной интеграционный механизм: retention, фильтрация и производительность ЖР не дают нужных гарантий доставки.

Событие должно порождать явную outbox-запись.

---

## 44. Не строить интеграцию на polling всего массива документов

Антипаттерн:

```text
каждую минуту найти все документы за год и сравнить с внешней системой
```

Используй event/outbox + cursor/repair reconciliation.

Допускается периодический **reconciliation job**, но как контроль расхождений, а не основной способ доставки каждого события.

---

## 45. Reconciliation

Даже при outbox/webhook должен существовать периодический механизм сверки:

```text
local binding ↔ remote object
local status ↔ remote status
expected amount ↔ remote amount
missing acknowledgement
stuck processing lease
```

Reconciliation не должен автоматически «чинить» бухгалтерский учет неизвестным образом. Он обнаруживает несоответствие и запускает безопасный recovery workflow.

---

## 46. Red flags — блокирующие антипаттерны

Не принимать PR, если присутствует хотя бы один пункт без явно одобренного исключения:

- модификация основной конфигурации без необходимости;
- `&Вместо` с копией большого типового метода;
- HTTP внутри транзакции документа;
- секрет в коде/логах;
- `Попытка ... Исключение ... КонецПопытки` без обработки;
- обход прав через широкий привилегированный общий модуль;
- запись напрямую в учетные регистры вместо штатной бизнес-операции;
- `.cfe` — единственный source of truth;
- нет idempotency для write API;
- нет timeout;
- бесконечный retry;
- polling тяжелых таблиц каждую минуту;
- работа только для первой организации;
- hard-coded URL production;
- отсутствие upgrade test на целевом релизе типовой конфигурации;
- отсутствие сценария recovery после «remote succeeded / local crashed».

# Профиль Orbitas для 1С:Предприятие

## 47. Роль коннектора Orbitas

Коннектор 1С является **адаптером**, а не clearing engine.

Он отвечает за:

```text
1C accounting/domain facts
        ↓
normalized Orbitas connector DTO
        ↓
Orbitas API / index / contracts
```

Orbitas core не должен знать про внутренние объекты `Документ.*`, `РегистрНакопления.*`, `Справочник.*` конкретной конфигурации 1С.

1С-адаптер не должен реализовывать внутри себя глобальный алгоритм clearing.

---

## 48. Anti-corruption layer

Обязательно создай слой mapping:

```text
1C object / register state
      ↓
1C adapter DTO
      ↓
Orbitas canonical obligation model
```

Не отправляй во внешний API «как есть» сериализованную ссылку/структуру 1С.

Mapping должен быть тестируемым отдельно от HTTP.

---

## 49. Stable source identity

Для каждого экспортируемого обязательства нужен стабильный `sourceId`, который не меняется при retry.

Он должен однозначно различать:

```text
information base / tenant
organization
source object kind
source object identity
obligation side / tranche if needed
```

Если используешь UUID объекта 1С, не забывай scope конкретной ИБ/организации.

---

## 50. Binding model

Храни отдельное соответствие:

```text
LocalSourceId
RemoteObligationId
RemotePassportId
CurrentExportVersion
LastPayloadHash
LocalState
RemoteState
LastConfirmedAt
```

Не добавляй десятки Orbitas-реквизитов в каждый типовой счет/реализацию, если то же можно хранить в собственном регистре расширения.

---

## 51. Извлечение обязательств

Для AR/AP определяй канонический бизнес-факт на уровне целевой конфигурации — не по «названию документа», а по фактической семантике долга.

Требуется явно определить:

```text
issuer/debtor
creditor
organization
document/source id
currency
original amount
outstanding amount
due date
state
quality/source metadata
```

Не предполагается, что один документ = одно obligation во всех конфигурациях. Mapping может зависеть от аналитик, договоров, этапов и расчетных документов.

---

## 52. Не менять учет по settlement instruction

Ключевой invariant Orbitas:

```text
settlement instruction != accounting settlement
```

Создание redirect instruction `A → C` не означает, что исходный долг в 1С уже погашен.

До подтвержденного факта исполнения:

- не менять взаиморасчеты;
- не закрывать документ искусственно;
- не подменять контрагента;
- хранить Orbitas state отдельно.

Это особенно важно, потому что в модели Orbitas/Byppay исходные invoice claims сохраняются до discharge, а instruction layer задает направление исполнения.

---

## 53. Подтверждение settlement

После подтверждения исполнения коннектор должен использовать **штатный учетный механизм целевой конфигурации**: допустимый платежный документ, зачет/корректировку или другой поддерживаемый бизнес-процесс.

Точный бухгалтерский документ **не должен быть универсально захардкожен в core adapter**, потому что БП/ERP/УТ и отраслевые решения могут отличаться.

Сделай strategy/adapter interface:

```text
DetectAccountingCapability()
PrepareSettlementPosting()
ValidateSettlementPosting()
ExecuteSettlementPosting()
```

и отдельные реализации для поддерживаемых конфигураций.

---

## 54. Orbitas outbox events

Минимальный набор событий MVP может включать:

```text
obligation.upsert
obligation.cancel
obligation.balance_changed
participant.upsert
settlement.accepted
settlement.accounting_confirmed
```

Точные события должны соответствовать API-контракту Orbitas и иметь versioned payload.

Не отправляй событие `invoice.paid` только потому, что Orbitas создал settlement instruction.

---

## 55. Orbitas inbound events

Типовые входящие события:

```text
obligation.accepted/rejected
settlement.proposed
settlement.locked
settlement.confirmed
settlement.expired
settlement.failed
```

Каждое событие сначала попадает в durable inbox, затем преобразуется в локальное состояние.

---

## 56. Consent и полномочия

Принятие redirect settlement должно требовать явной модели полномочий.

Не считай любого пользователя с доступом к форме счета уполномоченным принимать финансовое обязательство.

Разделяй роли, например:

```text
OrbitasRead
OrbitasOperator
OrbitasApproveSettlement
OrbitasAdmin
```

Набор ролей адаптируй к правилам 1С и БСП, но principle of least privilege сохраняй.

---

## 57. Orbitas quality/reputation metadata

Наблюдаемые качества и stake/guarantee state не должны переписывать бухгалтерские факты.

В 1С можно хранить projection/cache для UI, но source of truth каждого типа данных должен быть определен отдельно:

```text
accounting fact → 1C
Orbitas protocol state → Orbitas
local delivery/reconciliation state → connector storage
```

---

## 58. Orbitas multi-company

Каждая организация имеет отдельный config scope:

```text
Orbitas endpoint/environment
participant/passport binding
credentials or signer binding
feature enablement
policy defaults
```

Запрещено автоматически использовать credential организации A для документа организации B.

---

## 59. Orbitas test matrix

Помимо общей тестовой матрицы обязательно проверить:

```text
AR export
AP export
partial residual amount
credit note/correction
cancel/repost source document
multi-currency
2 organizations
same counterparty across organizations
same source event retried 10x
Orbitas accepts → 1C crashes → retry
webhook replay
settlement proposed but not accepted
settlement expired
settlement confirmed but accounting document fails validation
accounting posted only once
base configuration update changes intercepted method signature
```

---

## 60. Definition of Done — расширение 1С

Функция считается готовой только если:

- [ ] основная конфигурация не снята с поддержки без явного решения;
- [ ] surface заимствования минимальна;
- [ ] `&Вместо` отсутствует либо обоснован и покрыт regression test;
- [ ] роли расширения собственные и least-privilege;
- [ ] серверная проверка прав есть;
- [ ] транзакции корректны;
- [ ] внешних вызовов внутри транзакций нет;
- [ ] HTTP timeout задан;
- [ ] HTTPS server verification включена;
- [ ] secrets не попадают в Git/лог;
- [ ] outbox/inbox и idempotency покрывают write-интеграцию;
- [ ] retry/dead-letter/reconciliation определены;
- [ ] migration повторно запускаема;
- [ ] unit/integration tests проходят;
- [ ] ключевой E2E smoke проходит;
- [ ] EDT validation/стандарты разработки проходят без новых blocking diagnostics;
- [ ] `.cfe` воспроизводимо собирается из Git sources;
- [ ] проверена точная версия основной конфигурации и платформы;
- [ ] подготовлены release notes и rollback/disable procedure.

---

## 61. Mandatory Review Gate для Orbitas

Перед merge reviewer обязан ответить **да** на все вопросы:

1. Доменный факт 1С отделен от Orbitas protocol state?
2. `settlement instruction` нигде не трактуется как `invoice paid` до подтверждения?
3. Нет HTTP/blockchain-вызова внутри записи/проведения/транзакции?
4. Есть stable idempotency key?
5. Сбой после успешного remote write восстанавливается без дубликата?
6. Multi-company scope соблюдается?
7. Используется публичный/штатный учетный API вместо прямой правки учетных регистров?
8. Есть compatibility test с поддерживаемым релизом конфигурации?
9. Заимствование и method interception минимальны?
10. Любая операция, создающая финансовый эффект, требует корректных полномочий?

Если хотя бы один ответ «нет» — merge блокируется до исправления или оформленного architectural exception.

---

## 62. Алгоритм работы агента при новой задаче

Перед правкой кода:

```text
1. Определи точную base configuration + release.
2. Определи platform + compatibility mode.
3. Найди существующий публичный API/BSP extension point.
4. Проверь, можно ли решить без заимствования/перехвата.
5. Определи transactional boundary.
6. Если есть внешний side effect — спроектируй outbox/inbox/idempotency.
7. Определи права и organization scope.
8. Определи upgrade impact.
9. Напиши/обнови тесты.
10. Только после этого вноси код.
```

После правки:

```text
1. Validation.
2. Static analysis.
3. Tests.
4. Build .cfe.
5. Install into disposable exact-version IB.
6. Smoke.
7. Review borrowed objects / &Вместо / privileged sections.
8. Produce concise migration + compatibility note.
```

---

## 63. При конфликте требований

Приоритет:

```text
correct accounting semantics
> security / data isolation
> upgrade safety
> delivery guarantees / idempotency
> maintainability
> performance
> developer convenience
```

Не жертвуй корректностью учета ради удобства синхронизации.

---

## 64. Что агент должен сообщать в результате

Для существенного изменения возвращай краткий отчет:

```text
Changed:
- ...

Base compatibility:
- configuration/release
- platform

Extension touchpoints:
- borrowed objects
- intercepted methods
```
