# Drupal 11 Security, Access Control, and APIs

## Security Model

Apply four controls together:
1. validate and normalize input;
2. authorize the operation and data scope;
3. escape at output/serialization boundaries;
4. retain cacheability metadata for the authorization decision.

Do not treat UI visibility as authorization. Enforce permission at the route, entity, field, query, form, and API operation boundaries that expose the data.

## Route and Controller Access

```yaml
acme_catalog.settings:
  path: '/admin/config/acme/catalog'
  defaults:
    _form: '\Drupal\acme_catalog\Form\CatalogSettingsForm'
    _title: 'Catalog settings'
  requirements:
    _permission: 'administer catalog settings'
```

Use `_permission`, `_role` only when truly appropriate, `_entity_access`, or a custom access checker service. Avoid custom callbacks when standard requirements suffice.

A custom access checker must return `AccessResultInterface`, not a plain boolean:

```php
public function access(AccountInterface $account): AccessResultInterface {
  return AccessResult::allowedIfHasPermission($account, 'view catalog report');
}
```

Add cache contexts/dependencies to conditional results:

```php
return AccessResult::allowedIf($is_owner)
  ->cachePerUser()
  ->addCacheableDependency($entity);
```

## Entity and Field Access

- Call `$entity->access('view', $account, TRUE)` to obtain the full access result and preserve its cacheability.
- Implement access control handlers for custom entity types; reserve hooks for cross-entity alteration.
- Check field access when manually rendering/normalizing fields.
- Test allowed, neutral, forbidden, unpublished, revision, translation, and ownership cases.
- Ensure list queries do not reveal inaccessible records through counts, filters, labels, or timing behavior.

## Entity Queries

Always declare access behavior:

```php
$ids = $storage->getQuery()
  ->accessCheck(TRUE)
  ->condition('status', 1)
  ->range(0, 50)
  ->execute();
```

`accessCheck(FALSE)` is acceptable only for controlled internal operations (for example, an administrative queue worker) where authorization is enforced before entry. Document it in code and add a test showing why it cannot be reached by an unprivileged caller.

## Database Safety

Use entity storage when possible. For custom queries, use Drupal's Database API and placeholders/conditions:

```php
$result = $this->database->select('acme_item', 'i')
  ->fields('i', ['id', 'label'])
  ->condition('owner_id', $account->id())
  ->range(0, 50)
  ->execute();
```

Never concatenate input into SQL, table names, field names, expressions, or sort directions. Whitelist dynamic identifiers and directions.

## XSS and Output Safety

- Return render arrays and let Twig auto-escape variables.
- Use `MarkupInterface`/`Markup::create()` only for trusted, reviewed markup generated by the application.
- Avoid Twig `|raw`; if required, explain and test the trust boundary.
- Use `Html::escape()` for plain text constructed outside Twig and `Xss::filter()` with a deliberate allowlist for constrained HTML.
- Use `Url` and `Link` APIs rather than concatenating href attributes.
- Never render untrusted values through `#markup` without escaping/filtering.

## Forms, CSRF, and State-Changing Requests

Form API supplies CSRF protection for standard forms. For non-form state-changing routes:
- use non-GET methods;
- use `_csrf_token: 'TRUE'` where applicable;
- require authentication and operation-specific permission/access;
- validate request content type and payload;
- enforce replay/idempotency semantics for webhooks and payments.

Never mutate state on a GET request. Do not trust hidden fields, client-computed prices, entity IDs, or redirect destinations.

## Files and Media

- Use managed files/media entities, validators, and stream wrappers.
- Enforce extension, size, MIME/content validation, and upload permissions.
- Store sensitive files in a private filesystem and serve them through access-controlled delivery.
- Prevent executable upload paths; never permit PHP or server-executable files in public storage.
- Sanitize filenames and do not expose internal filesystem paths.
- Include file/entity access in download response cache metadata.

## Secrets and Environment Configuration

Keep secrets out of:
- Git;
- exported configuration;
- config entities;
- logs, traces, and exception messages;
- client-side `drupalSettings`.

Inject secrets from a secret manager or environment into [`settings.php`](web/sites/default/settings.php) overrides. Rotate credentials after leakage and invalidate sessions/tokens as required.

## JSON:API, REST, and Custom APIs

Prefer core JSON:API for conventional CRUD over content entities. Add custom endpoints only when business semantics, aggregation, or an external contract requires them.

For every API:
- document authentication and authorization per operation;
- minimize exposed resource types/fields and disable unused resources;
- enforce entity and field access;
- paginate and cap collection sizes;
- validate filters, sorting, includes, and sparse fieldsets;
- return cacheable responses with dependencies;
- define stable errors and avoid stack traces/sensitive context;
- apply rate limits at edge/application layers where abuse is plausible;
- protect write operations against replay and race conditions.

For custom normalized/serialized properties, never unsafe-unserialize user-controlled data. If legacy serialized values must be decoded, disallow object classes:

```php
$value = unserialize($payload, ['allowed_classes' => FALSE]);
```

Prefer JSON with explicit schema validation over PHP serialization.

## Headers, Sessions, and Browser Security

- Enforce HTTPS and secure/properly scoped cookies.
- Configure a tested Content Security Policy, HSTS, `X-Content-Type-Options`, frame controls, and referrer policy at the edge/web server.
- Avoid overly broad CORS; permit only required origins, methods, and headers.
- Do not cache personalized/session responses publicly.
- Use SameSite cookies consistent with integrations and test login/payment redirects.

## Dependency and Advisory Management

```bash
composer audit
composer outdated 'drupal/*' --direct
drush pm:security
```

Subscribe to Drupal security advisories, update core/contrib promptly, and audit abandoned packages/modules. Keep `composer.lock` committed and run installs with `composer install`, never production-time unconstrained updates.

## Security Checklist

```text
□ State-changing routes are non-GET, CSRF-protected, authenticated, and authorized
□ Route, entity, field, query, and API access are enforced and tested
□ AccessResult and entity dependencies bubble into cache metadata
□ Every entity query explicitly calls accessCheck(TRUE/FALSE)
□ No concatenated SQL or unvalidated dynamic identifiers
□ No untrusted #markup, Markup::create(), Twig |raw, or unsafe unserialize()
□ Uploads validate content/size/type and sensitive files use private storage
□ Secrets stay outside Git, config export, logs, and drupalSettings
□ APIs cap pagination, minimize fields, validate filters, and rate-limit abuse paths
□ Composer/Drupal security advisories are checked in CI and operations
```
